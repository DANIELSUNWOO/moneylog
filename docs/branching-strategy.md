# Git 브랜치 전략

## 배경

지금까지는 속도를 위해 로컬에서 바로 `main`에 커밋하고 push하는 방식으로 진행했다. 초기 셋업 단계에서는 합리적인 선택이었지만, 프로젝트가 "배포되는 서비스"로 굳어진 지금은 두 가지 이유로 브랜치 전략이 필요하다.

1. **`main`이 곧 배포 후보다.** CD 워크플로우(`cd-backend.yml`, `cd-frontend.yml`)가 `main`을 대상으로 하는 이상, `main`에 실수로 깨진 코드가 올라가면 다음 배포 시도가 그대로 실패하거나(최악의 경우) 깨진 채로 배포된다. CI를 통과하지 않은 코드가 `main`에 올라갈 수 없게 강제하는 장치가 필요하다.
2. **커밋 이력이 곧 결과물이다.** 해커톤 심사 자료로 GitHub 저장소를 그대로 제출한다. PR 단위로 정리된 이력은 "기능 단위로 작업하고 검증 후 병합했다"는 걸 코드만으로 보여준다.

1인 프로젝트라 코드 리뷰를 받을 사람은 없지만, 그렇다고 브랜치 전략 자체가 무의미해지는 건 아니다 — PR을 여는 순간 CI가 자동으로 돌고, "머지하기 전에 한 번 더 확인한다"는 최소한의 마찰이 생긴다. 이 마찰이 실수를 잡아내는 안전장치다.

## 브랜치 모델: Trunk-based, 장수 브랜치는 `main` 하나

`develop` 같은 별도의 장기 브랜치는 두지 않는다. 프로젝트 규모(1인, 3주)에서는 브랜치가 여러 개면 관리 비용이 이득보다 크다. `main`은 항상 배포 가능한 상태를 유지하고, 모든 작업은 `main`에서 갈라져 나온 단명(short-lived) 브랜치에서 진행한 뒤 PR로 다시 합류한다.

## 브랜치 네이밍

기존에 써왔던 `feature/F-10-dockerize`, `feature/F-14` 관례를 그대로 규칙화한다.

| 접두사 | 용도 | 예시 |
|---|---|---|
| `feature/F-XX-설명` | `requirements.md`의 기능 ID에 대응하는 기능 작업 | `feature/F-17-branch-strategy` |
| `fix/설명` | 버그 수정 | `fix/cors-signup` |
| `docs/설명` | 문서만 변경 | `docs/terraform-import` |
| `chore/설명` | 기능 외 변경(설정, 의존성, CI 등) | `chore/branch-protection` |

## 작업 흐름

```powershell
git checkout main
git pull
git checkout -b feature/F-XX-설명

# 작업 및 커밋 (로컬에서는 작은 단위로 여러 번 커밋해도 무방)

git push -u origin feature/F-XX-설명
```

이후 GitHub에서 PR을 열고(`base: main`), CI가 통과하는지 확인한 뒤 **Squash and merge**로 병합한다. squash를 쓰는 이유는 로컬에서 쌓인 "오타 수정", "다시 시도" 같은 잡다한 커밋들이 `main`에는 PR 하나당 깔끔한 커밋 하나로만 남게 하기 위해서다 — `main`의 히스토리가 곧 "기능 단위 변경 이력"이 된다. 병합 후에는 브랜치를 삭제한다(원격은 GitHub가 병합 시 자동으로 삭제 버튼을 제공, 로컬은 `git branch -d feature/F-XX-설명`).

## GitHub 브랜치 보호 규칙 (`main`)

- **PR 필수** — `main`으로의 직접 push 차단.
- **필요 승인 수: 0** — 1인 프로젝트라 스스로 자기 PR을 승인할 수 없으므로, "PR을 통해서만 병합 가능"은 유지하되 승인 자체는 요구하지 않는다.
- **상태 검사(CI) 통과 필수** — 백엔드 CI 워크플로우가 성공해야만 병합 버튼이 활성화된다.
- **관리자에게도 규칙 적용** — 저장소 소유자(본인)도 예외 없이 규칙을 따르게 해서, "귀찮으니 이번만 직접 push"를 구조적으로 막는다. 정말 급한 상황에서는 규칙을 일시적으로 끄고 처리한 뒤 즉시 다시 켠다(이 자체를 예외 처리 원칙으로 남긴다).
- **force push / 브랜치 삭제 금지** — `main`의 이력이 뒤바뀌거나 사라지는 걸 막는다.
- **병합 방식은 Squash만 허용** — 저장소 설정(Settings → General → Pull Requests)에서 "Allow merge commits"와 "Allow rebase merging"을 끄고 "Allow squash merging"만 남긴다.

## 예외 처리 원칙

CI가 인프라 문제(예: 외부 서비스 장애)로 막혀 있는데 정말 급한 수정이 필요하면, 브랜치 보호 규칙을 관리자 권한으로 일시적으로 끄고 병합한 뒤 원인을 파악해 즉시 규칙을 다시 켠다. 이 경우는 반드시 커밋 메시지나 PR 설명에 "왜 규칙을 우회했는지"를 남긴다.
