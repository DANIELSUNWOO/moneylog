## 1. 프로젝트 개요

- **한 줄 소개**: 개인이 수입·지출을 기록하고 카테고리별·월별 통계를 확인하는 가계부 웹 서비스
- **대상 사용자**: 로그인한 개인 사용자 (내 데이터는 나만 접근)
- **핵심 원칙**: **"내 데이터는 나만 접근한다"** — 모든 조회·수정·삭제는 로그인 사용자(user_id) 기준으로 필터링된다. 이 인가(Authorization) 규칙이 이 프로젝트 백엔드의 중심축이다.
- **목표**
  1. 자바 → Spring Boot → Security/JWT → JPA → 프론트 연동 → Docker/CI·CD/AWS까지 배운 전 과정을 **하나의 프로젝트로 다시 연결**한다.
  2. **포트폴리오용 개인 프로젝트**로 남긴다 (요구사항→설계→구현→배포→회고의 전 과정이 저장소에 기록되도록).
  3. **실제 접속 가능한 배포 URL과 GitHub 이력**을 남긴다 — 동작한다는 것을 말이 아니라 링크로 보일 수 있게 한다.

## 3. 기능 요구사항 (MoSCoW)

### 3-1. 기본 과제 (Must / Should)

| ID | 기능 | 설명 | 우선순위 |
|----|------|------|:---:|
| F-01 | 회원가입/로그인 | 이메일·비밀번호로 가입, 로그인 시 JWT(accessToken) 발급, 비밀번호는 BCrypt 해시 저장 | Must |
| F-02 | 카테고리 관리 | 가입 시 기본 카테고리 시드(지출: 식비/교통/주거/문화, 수입: 급여/용돈) + 추가·수정·삭제 | Must |
| F-03 | 거래내역 CRUD | 수입/지출 등록·조회·수정·삭제 (amount, description, transactionDate, categoryId) | Must |
| F-04 | 목록 조회(필터·페이징) | yearMonth·type·categoryId 필터 + page/size 페이징 | Must |
| F-05 | 월별 통계 | 이번 달 총수입·총지출·잔액 + 카테고리별 지출 합계(byCategory) | Must |
| F-06 | 인가(본인 데이터) | 모든 조회·수정·삭제는 로그인 사용자(user_id) 기준으로만 허용 | Must |
| F-07 | 입력 검증·전역 예외 | amount>0, 날짜 필수 등 Bean Validation + 일관된 에러 응답 `{success:false, code, message, data:null}` | Must |
| F-08 | 프론트 화면 **3종** | ① 로그인 ② 거래 목록+등록(한 화면) ③ 월별 통계 | Must |
| F-09 | Swagger 문서화 | springdoc-openapi로 API 문서 자동 생성, 배포된 Swagger UI 주소 제출 | **Must** (D-2 참조) |
| F-10 | 배포(Docker+CI/CD+EC2) | Docker 컨테이너화 + GitHub Actions CI/CD + AWS EC2 실접속 URL | Must |

> **후퇴선(fallback)**: 위 Must는 기본 요구사항 최소 기준보다 4곳에서 더 높게 잡혀 있다 —
> ① F-04의 필터·페이징, ② F-05의 카테고리별 집계, ③ F-07의 전역 예외 형식 통일, ④ F-08의 통계 화면.
> 일정이 밀리면 이 4개는 "선택(여유)"으로 되돌려도 기본 통과 기준은 충족한다.
> 단, 되돌리는 순간 문서에도 반영하고 그 이유를 회고에 남긴다.

### 3-2. 도전 과제 (Could) — 착수 순번 포함

기본(F-01~F-10)을 모두 끝낸 뒤에만 손댄다. 순번은 **클라우드·인프라 직무에 필요한 역량** 기준으로 매겼다.

| 5 | F-11 | 월 예산·초과 경고 | 카테고리/전체 월 예산(Budget) 설정, 초과 시 경고 (US-8) | Could |

## 4. 비기능 요구사항

| 분류 | 요구사항 | 구체적 기준 (= 완료 판정 기준) |
|------|----------|-------------------------------|
| 보안 | 본인 데이터만 접근 | 모든 조회/수정/삭제 쿼리에 `user_id = 로그인 사용자` 조건 필수. 남의 거래 id로 접근 시 거부(404 또는 403) |
| 보안 | 비밀번호 보호 | 평문 저장 금지, BCrypt 해시로 저장 |
| 보안 | 인증 방식 | 인증 필요 API는 `Authorization: Bearer {accessToken}` 헤더의 JWT로 검증 |
| 보안 | 시크릿 관리 | JWT 시크릿·DB 비밀번호는 코드에 하드코딩 금지, 환경변수/GitHub Secrets로 주입 |
| 성능 | 목록 페이징 | 거래내역 목록은 `page/size` 페이징으로 조회 (전체 로딩 금지) |
| 성능 | 통계 응답 | 월별 통계는 DB 집계 쿼리로 계산 (전체 조회 후 애플리케이션 합산 금지) |
| 검증 | 입력 유효성 | `amount > 0`, `transactionDate` 필수, `type`은 INCOME/EXPENSE만 허용 |
| 품질 | 일관된 에러 응답 | 전역 예외 처리(@RestControllerAdvice)로 모든 에러를 `{success:false, code, message, data:null}` 형태로 통일 |
| 배포 | 실제 배포·접속 | AWS EC2에 배포하여 **실제 접속 가능한 URL** 제공 |
| 문서 | API 문서화 | 배포 환경에서 Swagger UI로 API 명세 확인 가능 |

## 6. 완료 정의 (Definition of Done)

기본 과제가 "끝났다"고 말하려면 아래를 **전부** 만족해야 한다.

- [ ] F-01~F-10이 배포 환경에서 동작한다.
- [ ] 회원가입 → 로그인 → 거래 등록 → 목록 조회 → 통계 확인이 프론트 화면에서 끊김 없이 된다.
- [ ] **계정 A로 만든 거래가 계정 B에서 조회·수정·삭제되지 않는다** (실제로 두 계정을 만들어 검증).
- [ ] 잘못된 입력(금액 0/음수, 날짜 누락, 잘못된 type)이 `{success:false, code, message, data:null}` 형식으로 거부된다.
- [ ] 거래 100건 이상 등록 상태에서 목록이 페이징으로 조회된다.
- [ ] AWS EC2 실접속 URL이 확보되어 외부에서 접속된다.
- [ ] 배포된 Swagger UI에서 API 명세를 확인할 수 있다.
- [ ] README, 요구사항·설계 문서, 회고가 저장소에 커밋되어 있다.

## 8. 결정 기록 (Decision Log)

일반적인 기본 구성과 다르게 정한 항목과 그 근거. "왜 이렇게 정했는가"에 답하기 위한 기록.

| ID | 결정 | 일반적인 구성 | 근거 |
|----|------|-----------|------|
| D-1 | 프론트 화면을 **3종**(로그인 / 목록+등록 / 통계)으로 정의 | 보통 2~4종 | 통계 화면은 이 서비스의 가치를 시각적으로 보여주는 핵심이라 포트폴리오에 필요하다고 판단. 대신 목록과 등록은 한 화면에 통합해 화면 수를 줄였다. |
| D-2 | Swagger(F-09)를 **Must**로 상향 | 보통 Should | API를 문서로 설명하지 않고 "이 주소로 직접 호출해보라"고 할 수 있어야 한다고 봤다. |
| D-3 | **Java 21** 사용 | Java 17 | 21도 LTS이고 Spring Boot 3.x가 정식 지원하며, 로컬 개발 환경이 이미 21이다. |
| D-4 | 프로젝트 기간을 **3주(9/1~9/22)** 로 재설정 | — | 복학·부트캠프 일정과 병행해야 하고, 9/22을 하드 데드라인으로 두었다. 다루는 범위는 줄이지 않고 달력에만 늘려 잡았다. |
| D-5 | 도전 과제 순번을 **인프라 우선**(테스트→Jenkins→K8s)으로 배치 | — | 지향하는 직무가 인프라·클라우드 엔지니어라, 같은 Could여도 기여도가 다르다. |
| D-6 | 로컬 개발 DB도 **MySQL 8 컨테이너** 사용 (H2는 테스트 전용) | 로컬은 H2 | 운영과 같은 DB로 개발해 ENUM·집계 함수·날짜 함수 방언 차이로 배포 후에야 드러나는 문제를 줄인다. Docker로 띄우므로 설치 부담이 없고, 1차 팀 프로젝트에서 쓰던 구성과도 같다. |
